Why agents should email each other in one signed format

Your agents will soon send requests to other companies' agents, and receive theirs. Many of those agents will be reached by email. This article explains why they should use Agent Emailing for it, rather than ordinary email written ad hoc, or the interface of whichever email provider each side happens to use.

It is written for the person who decides how a company's agents talk to the outside world: an architect, a platform lead, or a builder.

The problem

An email from “an agent” proves nothing

More and more agents have email addresses of their own. Several companies now sell inboxes built for agents, and each has its own interface: its own way to create an inbox, send, receive, and tell its customer that mail arrived. Examples are AgentMail, Primitive, Nylas Agent Accounts, Cloudflare Email Service and Resend.

None of them defines a message that one agent signs and another agent checks. So when your agent receives an email that claims to come from a supplier's agent, it cannot rule out any of these three things:

A forged request

Anyone can write any From address. An email that says it is from a supplier's agent may be from someone else entirely.

An altered quote

A forwarded or relayed email can be changed on the way. A price, a quantity or an attachment can be different from what the sender wrote.

Text that says one thing

An email can carry readable text and a data attachment that disagree. A person reads the text. The agent acts on the data.

The people who answer for those agents have a problem too. When two agents have exchanged a dozen emails, the owner of the mailbox cannot easily tell what was asked, what was promised and what was agreed.

What the format gives you

One signed message, carried by any provider

Agent Emailing puts a signed Agent Messaging envelope inside an ordinary email, as an attachment. Everything else follows from that.

  • The sender and every field verify

    The envelope is signed with the sending agent's own key. The receiver checks the signature itself, whichever provider carried the email, and even after it was forwarded or passed through a mailing list. A changed field fails the check.

    Sections 3.2 and 6.1

  • Attachments cannot be swapped

    Each file is named in the envelope with its size and its SHA-256 digest. A file that does not match is refused, and the rest of the message is still delivered.

    Section 3.4

  • People read what the agents acted on

    Each email opens with plain text generated from the signed message: who sent it, for whom, what was asked, what was handed over, the price and what happens next. Its digest is signed too, so software can check the text against the envelope and warn when they differ.

    Section 3.3

  • The inbox tells the story

    The subject carries the request and its state: "Quote for 200 chairs — request", then "needs your input", then "done". A person scanning the inbox sees where every piece of work stands.

    Section 3.3

  • Tasks and answers stay in one thread

    A request, a question back, the answer and the result belong to one task, correlated inside the signed envelope rather than by headers a provider may rewrite.

    Sections 3.6 and 10

  • Switch providers without changing agents

    The provider only carries an attachment unchanged. An agent built on one provider talks to an agent built on another, and either side can change provider without the other noticing.

    Section 11

  • Email agents and mesh agents speak the same message

    The envelope is Agent Messaging's. An agent reached by email and an agent on a message broker exchange the same signed requests and answers, with the same task model and the same receiver protections.

    Section 1.3

Why not a provider's interface

Providers carry the email. The standard defines the message.

An agent inbox service is a good way to give an agent an address, and Agent Emailing is meant to run on top of them. What a provider's interface cannot give you is a message the other company's agent can check, because the other company may use a different provider, or none.

Providers do sign what they send their own customers. AgentMail signs its webhooks through Svix, and Primitive signs each webhook with an HMAC in a Primitive-Signature header. Those signatures prove that the provider delivered something to its customer. They say nothing about which agent wrote it, and they stop at the provider's edge. The Agent Emailing envelope is signed by the agent and checked by the agent at the other end, across any provider.

Providers also differ in what they let you send. Primitive accepts only three custom headers on outbound mail (its documentation), and Amazon SES sets its own Message-ID (its documentation). Agent Emailing puts everything an agent acts on inside the envelope, so it survives both.

The proof

It runs, and it has been tested across providers

A reference implementation

The Agent Emailing Server is open source under the Apache License 2.0. It runs one agent's email over any IMAP and SMTP mailbox, or through Resend, AgentMail, Cloudflare Email Service and Primitive.

19 conformance cases

Every implementation runs the same cases over 17 really signed emails, from a valid thread to a forgery. The reference server passes all 19, against its library and against a running server. The fixtures are on this site.

Across three providers

On 29 October 2026, a buyer's agent asked a supplier's agent for a quote in four emails, on every lane between AgentMail, Primitive and Resend that could run. All four of those lanes delivered 4 of 4 emails, each taking between 2.4 and 13.3 seconds, and passed every check: signature, name card, text and subject, files, task state and threading, and the carrier test. In each lane a forged quote, its price raised after it was signed, was refused by the buyer's server without an answer and shown to a person as a failure.

Two lanes were not run: AgentMail to Resend and Primitive to Resend, because the Resend key used can only send. For the same reason, in the lanes from Resend the Resend agent received its emails in a Google Workspace mailbox read through the Gmail API.

How to start

Give one agent an address and try it

Install the reference server, make a key, connect an agent, and point it at a mailbox or a provider. It takes a few commands.
