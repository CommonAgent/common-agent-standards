An example

What a person sees

Ana Lima's scheduling agent asks the bookings agent at example.com to book a meeting. The bookings agent offers two times, Ana's agent picks one, and the bookings agent sends the invitation. Four emails pass between the two agents. This is how they look in the mailbox of Ana's agent.

Each email opens with text generated from the signed message, so Ana can read what was asked, what was handed over and what happens next without opening an attachment. Every email on this page is a conformance fixture, and every signature is real. The keys are published test keys and control nothing.

The thread

Book a meeting, in four emails

The badges are what software that checks Agent Emailing shows after it checks each email. A mail program that does not check Agent Emailing shows the same emails and the same text, without the badges. This page computes every badge from the fixture it sits on, and shows a badge only when that check passes.

The badges

What each badge means

A failure

An email that fails the trust checks

Someone took Ana's signed request, changed it to ask for 90 minutes with a 20.00 USD limit and a charge to her account, and sent it from an address that is not on her name card. Every check below is computed from the email itself. The signature fails because the envelope changed after it was signed. The sender check fails because the address is not on the card. The text check fails because the text is not the text that was signed.

This is fixture 17-forged.eml, case e19.

A warning

When the text does not match

This request was signed asking for 30 minutes with a price limit of 2.00 USD. Its text was then changed to say 90 minutes and 20.00 USD. The signature still verifies, because the envelope was not touched. The text check fails, so checking software warns the person and shows what the signed message says. The bookings agent never reads the text at all.

This is fixture 16-text-mismatch.eml, case e18.

What to notice

  • Correlation is inside the envelope. The answer to the request carries the request's id in in_reply_to, and every message after the first carries the same task_id. The email Message-IDs are not the envelope ids (section 3.6).
  • The envelope's meta.agent_emailing signs the subject and the digest of the text. That is what lets software tell whether the text a person reads is the text the sender signed.
  • Each file is a cid: reference with its size and digest, so the unsigned file part cannot be swapped (section 3.4).
  • Each agent found the other's address on its verified name card. A handle has the form of an email address, but it is not one, and nobody sends mail to it (section 5.2).

The order of checks

A receiving agent handles each email in the order of section 7.2:

  1. It checks the provider's own notice signature, where the provider sends one.
  2. It parses the email and finds exactly one envelope part. Two are refused (fixture 10).
  3. It verifies the envelope's signature. A changed value fails here (fixtures 07 and 17).
  4. It checks for a duplicate, then the seven-day mailbox window, then that to is its own key (fixtures 05 and 06, case e14).
  5. It decides the sender's standing and applies its owner's admission rules (EXT-6).
  6. It checks each file's size and digest against the envelope (fixture 09).
  7. It hands the envelope to the agent, with the payload text fenced as Agent Messaging §22.6 requires. It never reads the human part.

Software that shows the email to a person checks the human part and the subject against the envelope, as section 3.3 says, and warns when they differ (fixture 16).
