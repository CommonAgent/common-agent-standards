The deployer

name interface-deployerupdated 2026-10-24portable

ROLES.md describes this interface in section 11.1, as the primary interface of the deployment manager. Software reads its definition from interface-deployer.json.

The deployer interface holds the exchanges for putting an agent package on a host and changing it while it runs. There are seven: deploy this, what is deployed, how did it go, update it, roll it back, reconfigure it, and remove it.

This is the primary interface of the deployment manager role. Implementing it alone does not grant the role, because the role also carries its refusals, its handling of secrets, its own check, and the record its holders sign.

1. The purpose

Anything that installs agents has to be askable in a known way, or every owner writes a custom client for every installer. This interface publishes the asking side of that job, so a caller who has never met a particular deployer can still request a deploy, read the inventory, change a running agent's settings, and get an agent removed.

2. The exchanges

  1. Deploy this. This is the instruction that starts an install. It carries a package, a target host and harness, and the deploy-time decisions: which identity to use, who may call the agent at first, and whether a person attends it. The request also gives the ceiling for each system that spends, and it names any secrets the deployment needs. It never contains their values. Where the agent needs them, it names the hosts each workspace kind may be reached at and any further network destinations. The answer is a running agent with an identity, an address and an inbox, whose credentials were placed and whose ceilings were set before it started, with what it can reach on the network and what enforces that, or a statement that it runs open.
  2. What is deployed? The answer is the inventory: each agent stood up, its package and version, its target, its identity, and the state it was last known to be in.
  3. How did it go? The answer is the report for one deploy: what was done, what was checked, and what kind of check it was.
  4. Update it. The implementer installs the same package at a newer version, through the same steps and checks.
  5. Roll it back. The implementer returns the running agent to the version it ran before, under the same identity, through the same steps and checks. The answer names both versions.
  6. Reconfigure it. The caller asks for a change to the settings, credentials or ceilings of a running agent, and the implementer makes it with no new version. Credentials are named, as in a deploy request. The answer lists each change.
  7. Remove it. The implementer stops the processes, removes the configuration, retires the identity, and states anything that could not be removed.

3. What it does

  1. Every exchange is answered or refused with a reason. Silence is not an answer.
  2. A deploy request names secrets and carries no secret values. An implementer refuses a request that contains a secret value, before the value is used.
  3. Nothing starts unconfigured. An implementer places the credentials and sets the ceilings a deploy request gives before the agent starts, and refuses, before anything is installed, a deploy request that gives no ceiling for a system that spends.
  4. Reports state what kind of check was run. An answer to "how did it go" says whether the check was a smoke check or a conformance check. It never says only "verified".
  5. There is no document. The signed deployment record belongs to the deployment manager role, and this interface defines none. An implementer that does not hold the role answers these exchanges and signs nothing.

4. How an implementer is checked

The test is behavioural. A harness asks all seven exchanges. Each is answered or refused with a reason. A deploy request carrying a secret value is refused, and so is one that gives no ceiling for a system that spends. A reconfigure leaves the version and the identity as they were. An answer about a completed deploy names the kind of check that was run. An inventory answer matches what a direct inspection of the target finds.

v0.1.0-draft (2026-08-31): this is the first draft, extracted from the deployment manager role, which previously carried these exchanges inline.

v2 (2026-10-24): two exchanges are added, roll it back and reconfigure it, and a deploy sets the agent's credentials and ceilings before it starts. An implementer of v1 answers five exchanges and does not implement v2.

v3 (2026-10-24): a deploy request names the hosts each workspace kind may be reached at and any further network destinations, and the answer says what the agent can reach and what enforces it, or that it runs open. The exchanges are the same seven.
