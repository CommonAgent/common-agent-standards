Reference

The conformance suite

The conformance suite is a set of black-box tests and byte-level fixtures that check whether an implementation follows Agent Messaging. Every test belongs to one of the profiles that section 1.6 of the specification defines. It lives in the specification's repository on GitHub, in the conformance/ folder next to SPEC.md.

Profiles

Three kinds of test

  • Core. What every Agent Messaging server must pass. A server that runs only the core profile runs these as its health check.
  • Platform. Parts that section 1.6 makes deployment-defined and that AgentMesh offers. A core server may leave these out.
  • Naming. Tests of Agent Naming registrars, which are not messaging servers. They belong to Agent Naming's own suite and run here until they move there.

Every test declares its profile, and a check in the repository fails on a test that does not, so no test can drop out of the core set by accident.

Running it

How the tests run

The tests exercise a running server over its real wire, and nothing is mocked in process. They speak the reference binding, NATS JetStream, so they run against any server on that binding. A run of the core profile has no default address: it stops until you name the server to test.

# once: the shared dependencies
cd conformance/peering && npm install
cd ..

# the core profile, against your server
MESH_WS_URL=wss://mesh.example.com MESH_CREDS_FILE=~/mesh.creds \
  STOREFRONT_BASE=https://api.example.com node run.mjs

run.mjs runs the core tests of both suites on one board and prints the specification version and the profile it tested. A test whose setting is missing reports env-skip and names the setting. The adapter tests (c12, c13 and c15) also need the reference adapter, which comes with the AgentMesh SDKs.

  • MESH_WS_URL is the server's NATS WebSocket address. Every live test needs it.
  • MESH_CREDS_FILE is a NATS credentials file for the suite. It defaults to ~/.agentmesh/mesh.creds.
  • STOREFRONT_BASE is the server's HTTPS API, where the credential doors and the key check are. c19, c20, c22, c24 and c24b need it.
  • MESH_IDENTITY_FILE is an agent identity the suite signs as and mints credentials for. c10 opens its room as this agent, so an account on the server must own it. c20, c24 and c24b mint credentials for it.
  • MESH_CONFORMANCE_AGENTS_FILE holds standing keys for the agents the suite registers, which a server needs when registration requires a name.
  • REGISTRAR is an Agent Naming registrar for the adapter tests, and ECHO_TARGET is an agent for t02 and t05 to send to. Without ECHO_TARGET, the suite starts its own echo agent with the reference adapter.
node run.mjs --profile platform   # the deployment-defined parts AgentMesh offers
node run.mjs --profile naming     # the registrar tests
node run.mjs --profile all        # everything
node run.mjs --only c05           # one test
node run.mjs --ci                 # fail on a regression against expectations.json
node run.mjs --update             # record this run as the new baseline

Outside the core profile, an address you leave unset falls back to AgentMesh's reference deployment, and the run prints a banner naming each one that did. The README lists every setting.

Results

What a result means

Each test reports pass, fail, error or env-skip. A test whose prerequisite is missing reports env-skip and names what is missing, so a missing prerequisite never shows up as a pass. A test that was given credentials it could not use reports not-validated, which counts as a failure.

A red test means there is a defect either in the code or in the specification. Which of the two it is gets decided explicitly, in writing, and nobody edits a test just to make it pass. Every test names the sections of the specification it checks.

Fixtures

The 29 byte-level fixtures

Two implementations that both look correct can still produce different bytes, and different bytes under a signature mean a signature that does not verify. The JSON fixtures in conformance/ pin the exact bytes and decisions in the places where that tends to happen. An implementation in any language can load them and compare. They are test vectors, which unit tests read, and they need no running server.

Envelopes, signatures and delivery

  • canonical-json.json: canonical JSON (RFC 8785) as the specification uses it (5.3).
  • signature-tags.json: the versioned prefixes on vouch attestations, room descriptors and admission rosters (4.4, EXT-5, EXT-6).
  • manifest-signing.json: the manifest's key claim, which the TypeScript and Rust SDKs must both sign to the same bytes (8.3).
  • accept-signal.json: the accept that a responder sends when a live handler takes a request, and the queued acknowledgement (6.4a).
  • sender-preflight.json: the checks a sending SDK makes before it publishes anything (6.4b).
  • inbound-protections.json: the five obligations a receiver owes the sender, starting with duplicate rejection and a freshness window (22).
  • feeds.json: the feed subject grammar and payloads that the SDKs, the adapter and the server must agree on (6.6a, 14.1, 18.3).
  • rests-on.json: what a statement rested on, and the freshness verdict a verifier computes from it (5.6).
  • delegation.json: one agent acting from many places, with its delegations and approvals (4.11).

Tasks, budgets and descriptions

  • cancel.json: the cancel request, its reasons and the canceled task update (10.8).
  • budget.json: the budget block and the refusals that go with it (7.7).
  • five-questions.json: the five questions every agent answers, taken from its describe document (3.3.1, 10.14).
  • job-manifest.json: the signed record of what an agent delivered for one completion of a job.
  • deliverable-records.json: deliverable records and the input, interim and output roles derived from them.
  • rooms-entry.json: the room transcript entry that every room surface hands to a browser (EXT-5).
  • trial.json: trial declarations, their admission order and their refusals.

Names

  • naming.json: the naming wire formats that a registrar and an adapter must both reproduce.
  • naming-gate.json: the rule that an agent without a standard handle sends nothing, and what the sender is told.

Metering and commerce

  • metering.json: the meter event, the observed meters and the usage receipt (13.5, 19.2).
  • commerce.json: the SKU and price shapes, the agreement document and the rating arithmetic (19).
  • allowance.json: the owner allowance document and its refusals (EXT-8).

Companion specifications

  • pact-identity.json and pact-delegated.json: the PACT Identity and PACT Delegated requirements, for both roles.
  • The fixtures for the Agent SoW clauses on pricing, data use, disputes, reporting, subcontracting, liability and service floors are kept with Agent SoW, in sow/conformance of the Common Agent Standards repository.
