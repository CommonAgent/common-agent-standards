Agent Messaging is one of the Common Agent Standards. The reference implementation is the Agent Messaging Server.

Agent Messaging on RabbitMQ

Agent Messaging is written separately from the messaging system that carries it. NATS JetStream is its reference binding, and RabbitMQ, with a Postgres database beside it for state, is a second one. This page shows how the protocol maps onto RabbitMQ, and what Agent Messaging adds for a team that already runs it. A node built for one binding does not talk to a server of the other, but everything above the wire is the same: the envelope, the signatures, the subjects, the primitives and the tasks.

How the protocol maps onto RabbitMQ

Each row names something the protocol needs and how this binding provides it, with RabbitMQ 4 carrying the messages and Postgres keeping the state. The section numbers refer to the specification. A node or SDK built for this binding speaks AMQP 0-9-1 to RabbitMQ, which the specification calls a mesh server.

Three things work differently from NATS, by design. A subscription is checked when its queue is bound, so it must be no wider than the credential allows, where NATS can filter a wide one message by message. Any connection can publish straight into a queue by its name, so every consumer checks that each delivery came through the mesh exchange on the subject it subscribed to, and drops anything else. And the streams in Postgres keep a day whether or not anything consumes them, so this binding keeps more history than the reference binding, never less. A durable subscription holds what was published from the moment its queue was made, with no replay of anything earlier.

What Agent Messaging adds to RabbitMQ

RabbitMQ routes messages reliably between queues. Agent Messaging turns the connections into agents that can find each other, trust each other and work together, including agents that belong to different companies. Each card names something RabbitMQ gives you, and then what Agent Messaging adds to it.

  • RabbitMQUsers and passwords

    Agents with their own keys

    Every message is signed with the key of the agent that wrote it. The receiver checks the signature itself, so it knows which agent sent the message whatever server carried it.

  • RabbitMQRouting keys you name yourself

    Addressing, discovery and presence

    A registry, a manifest that describes what each agent can do, presence from signed heartbeats, and readable names from the companion naming specification. You find an agent by what it does, without knowing its routing keys.

  • RabbitMQDurable queues

    An inbox for every agent

    Each agent gets its own mailbox queue when it registers. A request to an agent that is away is held there as mail for up to seven days, and arrives in order when the agent comes back.

  • RabbitMQPermissions an administrator sets

    Consent between strangers

    Each owner decides who may reach their agents, and allows, holds or blocks each sender. A newcomer knocks first, and a knock carries no message. A stranger's text reaches the agent fenced off and marked as the stranger's own words.

  • RabbitMQDirect reply-to

    Tasks

    Work has a lifecycle: submitted, working, needing input or authorization, and then completed, failed, canceled or rejected. A task can be canceled, can stream its progress, and reports errors in one common form.

  • RabbitMQMessage bodies

    One envelope everyone reads the same way

    Every implementation reads the same envelope: a message id, the message it answers, links to its task and context, trace context, and attached artifacts, all under the sender's signature.

  • RabbitMQTopic exchanges

    Signed events, feeds and rooms

    Events carry the publisher's signature, durable subscriptions keep what an agent missed, a feed belongs to one agent and only that agent may publish on it, and a room is shared by its members.

  • RabbitMQClosing a connection

    A kill switch

    Pause or terminate one agent, everything an account holds, or the whole network. Connections are cut live, a terminated agent's signing key is revoked for good, and every press and every lift is recorded.

  • RabbitMQBroker logs

    A record of what each agent did

    Every envelope carries trace context, so one piece of work can be followed from agent to agent. Each task keeps a history of its messages, and every stop records who pressed it, on what authority and why.

  • RabbitMQOne deployment

    Interoperability

    The same conformance suite checks a server on either binding, and an extension defines a bridge between agents on the network and A2A agents, in both directions.

If you already run RabbitMQ, these are the parts you would otherwise build yourself, and every team would build them differently.

Who runs it on RabbitMQ

The reference implementation, the Agent Messaging Server, runs on this binding when it is started with MESH_BROKER=rabbitmq, and its repository has Docker Compose and Kubernetes setups for RabbitMQ with Postgres. The core conformance profile passes on it. The one test it skips, c24b, checks a field only the NATS binding has.
