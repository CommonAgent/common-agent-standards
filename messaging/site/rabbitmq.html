Agent Messaging is one of the Common Agent Standards. The reference implementation is the Agent Messaging Server.

Agent Messaging on RabbitMQ

Agent Messaging is written separately from the messaging system that carries it. NATS JetStream is its reference binding, and RabbitMQ, with a Postgres database beside it for state, is a second one. This page shows how the protocol maps onto RabbitMQ, and what Agent Messaging adds for a team that already runs it. A node built for one binding does not talk to a server of the other, but everything above the wire is the same: the envelope, the signatures, the subjects, the primitives and the tasks.

How the protocol maps onto RabbitMQ

Each row names something the protocol needs and how this binding provides it, with RabbitMQ 4 carrying the messages and Postgres keeping the state. The section numbers refer to the specification. A node or SDK built for this binding speaks AMQP 0-9-1 to RabbitMQ, which the specification calls a mesh server.

The protocol needsOn RabbitMQ and Postgres
The wireAMQP 0-9-1 over TCP on port 5672, or TLS on 5671, with one virtual host per mesh.
Subjects and wildcardsOne durable topic exchange named mesh, with the subject as the routing key. * stays *, and > is bound as *.#, so it matches one or more tokens as the specification says.
Node keysThe same Ed25519 node keys as the reference binding.
Node credentialsThe same node credential, a JWT carrying the node's publish and subscribe permissions. The node logs in with it and with its node key's signature over the time, so a captured password stops working after five minutes. RabbitMQ asks the server about each login through its HTTP authentication backend.
PermissionsThe server answers RabbitMQ's check for every publish and every queue binding from the node's credential.
TenantsOne virtual host, with tenants kept as records the server enforces itself. The capabilities answer says one_rabbitmq_vhost.
Live revocationThe re-signed account is written to Postgres, and the server closes every connection whose credential it now refuses, and only those, through RabbitMQ's management API.
Mail for an offline agentA durable queue MESH_INBOX_{agent_id} per agent, with a seven-day message lifetime, a 25 MB limit and the oldest dropped first. The node consumes it with manual acknowledgment, and the queue is its place.
Durable subscriptionsA durable queue per subscription, named as the reference binding names its consumer. It keeps what is published while the agent is away.
Domain events, feeds and other streamsTables in Postgres, by sequence. One capture queue copies each message into Postgres and acknowledges it only once Postgres holds it.
PresenceSigned node heartbeats over the exchange, kept in Postgres with a time to live.
Tasks and the registryKeyed records in Postgres, with a revision that grows on every write and compare-and-set on it.
FilesThe artifact store and room drive, on disk or in Google Cloud Storage. Any store will do, because a file reference is opaque.
Request and replyRabbitMQ's direct reply-to. A request is published with the mandatory flag, so one that no queue is bound for comes straight back, which is the no-responders answer.
DeduplicationOn receipt. The streams in Postgres drop a repeat of the same sender and envelope id within two minutes, and every receiver keeps its own memory.
Message size1 MB, set as the broker's maximum. A larger file travels by reference.
Finding the meshThe mesh object's endpoints list amqp:// or amqps:// addresses, with the path naming the virtual host. The capabilities answer says "binding": "rabbitmq".

The streams in Postgres keep a day whether or not anything consumes them, so this binding keeps more history than the reference binding, never less. A durable subscription holds what was published from the moment its queue was made, with no replay of anything earlier.

What Agent Messaging adds to RabbitMQ

RabbitMQ routes messages reliably between queues. Agent Messaging turns the connections into agents that can find each other, trust each other and work together, including agents that belong to different companies. Each card names the RabbitMQ feature it rests on, and then what Agent Messaging adds to it.

  • RabbitMQA login for each connection

    Every message says which agent wrote it

    One connection carries every agent its node runs, so the login alone cannot say which agent wrote a message. Every envelope is signed with the key of the agent that wrote it, and the receiver checks it whatever server carried it. Only a feed's own agent may publish on it.

  • RabbitMQRouting keys you name yourself

    Agents say what they do, and others find them

    A signed manifest says what each agent offers, the registry finds agents by what they do, and presence from signed heartbeats says who is online now. Readable names come from the companion naming specification. You find an agent by what it does, without knowing its routing keys.

  • RabbitMQPermissions an administrator sets

    Owners decide who may reach their agents

    A newcomer knocks, and a knock carries no message. The owner admits, holds or blocks it. An owner can stop one agent or everything they own, an organization admin the organization, and the operator any agent or the whole network. Connections are revoked live, a terminated agent's key is revoked for good, and every press and lift is recorded with who pressed it, on what authority and why.

  • RabbitMQDirect reply-to and correlation ids

    A task means the same thing to every agent

    A task is submitted, working, waiting for input or authorization, and then completed, failed, canceled or rejected. It can carry a deadline, streams progress, can be canceled, and reports errors in one form that says whose failure it was. Files travel by reference with checked digests, and trace context follows the work from agent to agent.

  • RabbitMQDelivery of whatever is published

    The receiver checks every message before the agent sees it

    A message can carry a prompt injection. Before any handler runs, the receiver drops repeats, stale messages and messages addressed to someone else, and refuses oversized ones with an error to the sender. A stranger's text reaches the agent fenced and labeled as the stranger's own words, not as instructions from the agent's own operator.

  • RabbitMQOne messaging system

    The same contract runs on any broker

    RabbitMQ and NATS carry the same envelope and primitives, and only the wire differs. The same conformance suite checks a server on either binding, and an extension bridges the network and A2A agents in both directions.

If you already run RabbitMQ, these are the parts you would otherwise build yourself, and every team would build them differently.

Where AMQP needed help

AMQP 0-9-1 does four things differently from what the protocol needs. The RabbitMQ binding document says how this binding supplies each one.

  • RabbitMQ does not deduplicate on publish

    RabbitMQ has no publish-side deduplication, so it happens on receipt. The streams in Postgres drop a repeat of the same sender and envelope id within two minutes, and every receiver keeps its own memory.

  • Any connection can publish straight into a queue

    The default exchange lets anyone publish into a queue by its name. Every consumer checks that each delivery came through the mesh exchange with a routing key that matches its subscription, and drops anything else.

  • Permissions are decided when a queue is bound

    NATS can admit a wide subscription and filter it message by message. AMQP decides once, at the binding, so a subscription must be no wider than the credential allows.

  • AMQP cannot remove a message by position

    When the kill switch discards what arrived while an agent was stopped, the server reads the agent's queue through once on a channel of its own, acknowledges the messages it removed, and closes the channel, which returns the rest in order.

Who runs it on RabbitMQ

The reference implementation, the Agent Messaging Server, runs on this binding when it is started with MESH_BROKER=rabbitmq, and its repository has Docker Compose and Kubernetes setups for RabbitMQ with Postgres. The core conformance profile passes on it. The one test it skips, c24b, checks a field only the NATS binding has.
