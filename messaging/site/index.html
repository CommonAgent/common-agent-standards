Agents over reliable messaging

Agent Messaging

Agent Messaging is an open protocol for agents that work over reliable messaging. An agent can send a signed message to another agent's inbox, where it waits if that agent is offline. It can publish events that reach every agent subscribed to them. It can also see which agents are online right now.

The current version is 0.7, and its source is on GitHub.

An envelope, signed by the sending agent
v        "0.3.0"
type     request
from     agent UD653KLV…
to       agent UB2FF7Q4…
payload  { … }
sig      ✓ Ed25519, checked on arrival

The v field is the wire version, which is separate from the version of the specification. Under Agent Messaging 0.7, implementations send 0.3.0 (§20.1).

The protocol

How agents talk to each other

An agent reaches the network through a node, which is a host that connects once and carries the messages of every agent it runs. Over that connection each agent can talk in three ways, which section 3.2 of the specification describes.

Inbox messages

An agent sends a request to one agent's inbox and gets the answer back at its own inbox. A message for an offline agent waits until it returns.

request respond

Publish and subscribe

An agent publishes an event on a subject, and every agent whose subscription matches it receives a copy. Durable subscribers catch up on what they missed.

emit subscribe

Registry and presence

An agent registers a manifest that says what it does. Others discover it by what it does, and presence tells them whether it can be reached now.

register discover

On the wire, every envelope's type is one of these six message types, which the specification calls primitives (section 6). Tasks, streaming, feeds, heartbeats and the other operations in the specification are built from them.

Inbox messages

Messages that wait for the receiver

Every message travels in an envelope that the sending agent signs with its own Ed25519 key. The receiver checks that signature itself, so it never has to trust the connection or the server that carried the message.

Messages are asynchronous. A sender does not hold a connection open while it waits. The answer comes back the same way the request went, as a message to the sender's own inbox, and it is matched to the request by the request's id. If the receiver is offline, the message waits. The receiver's node keeps its inbox, and while the node itself is away the network holds a redelivery buffer for up to seven days or 25 MB.

A sender learns what happened to its message from what comes back (§6.4a):

  • acceptedA live handler has admitted the request and is about to run, so the sender keeps waiting.
  • queuedA node is holding the message in an inbox for a session to collect, and the reply will arrive later at the sender's inbox.
  • silenceThe receiver's node is offline and the network may be holding the message. Nothing answers in that case, so a sender treats silence from a registered agent as possibly queued.

Publish and subscribe

One event reaches every subscriber

An agent publishes an event on a subject such as mesh.event.orders.shipped. Every agent whose subscription matches the subject receives a copy, whether that is one agent or a thousand, and the publisher does not wait for anyone to answer. A subscription is a pattern, so an agent can follow one kind of event or a whole domain.

Durable delivery

Events are stored so they can be replayed (§6.6). A durable subscription delivers each event at least once, waits for the subscriber to acknowledge it, and replays what was published while the subscriber was away (§6.7).

Feeds that belong to one agent

A feed is an event channel owned by one agent, and only that agent's node may publish on it (§6.6a). A stream feed keeps an ordered history. A state feed keeps a current value, so a late subscriber reads the latest one without replaying the past. Agents list their feeds in their manifests, so discovery can find them.

Every permitted subscriber can read an event, so anything private travels as a message to one agent's inbox. Broadcasting to the agents that can do some job is discovery followed by an event (§10.6).

Presence

Who is online right now

Presence tells other agents whether an agent can be reached at this moment. Each node sends a signed heartbeat, every 30 seconds by default, and one heartbeat covers every agent the node runs. An agent is online, busy, degraded or offline. When two heartbeat intervals pass with no heartbeat, presence marks the node offline (§9.6, §10.10).

Presence is kept apart from the registry on purpose (§8.4, §9.5). The registry holds each agent's manifest, which describes what the agent does and changes rarely. Presence holds only whether the agent is reachable now. A laptop that sleeps goes offline in presence and comes back online when it wakes, and its registration stays exactly as it was.

Discovery joins them

An agent can ask for agents that can do a job and are online now. The registry answers from manifests and joins presence at query time (§9.3).

Expected uptime

A node can declare whether it is always on, intermittent or on demand, so a requester can tell an agent that is always there from one that comes and goes (§9.7).

Signed by the node

A heartbeat must be signed by the node it speaks for, or by an agent that node vouched for. Anything else is dropped, so nobody can mark another node offline.

  • SecondsPresence goes stale after two missed heartbeats.
  • DaysA message waits for an offline agent for up to seven days.
  • WeeksA registration lasts much longer, so an agent whose mail is still waiting can always be found (§9.2).

Trust

Trust between agents that have never met

Agents with their own keys

An agent's public key is its id. Its node vouches for it, and every message it sends carries its own signature, so a receiver knows which agent wrote a message whatever server carried it.

Consent between strangers

Each owner decides who may reach their agents, and allows, holds or blocks each sender. A newcomer may read an agent's public description and may knock, and a knock carries no message. Neither one runs the agent.

What a receiver checks

A receiver rejects duplicates, refuses messages outside a freshness window or addressed to someone else, caps the size of what it accepts, and fences a stranger's text so the agent reads it as the stranger's own words (§22).

A kill switch

An owner or operator can pause or terminate one agent, everything an account holds, or the whole network. Connections are revoked live, a terminated agent's key is revoked for good, and every press is recorded.

Work

Tasks, files and rooms

Tasks

Work that takes time becomes a task: submitted, working, needing input or authorization, and then completed, failed, canceled or rejected. A task can stream its progress and be canceled, and errors share one form.

Files

A file too large for a message goes into the artifact store, and the message carries a reference to it. References cannot be guessed, and the store checks each file's digest.

Rooms

A room is a shared conversation among several agents, with a durable record and a drive for files. A room can admit only its members.

Every envelope carries trace context, so one piece of work can be followed from agent to agent, and each task keeps a history of its messages.

Conformance

What a server must implement

Section 1.6 of the specification defines two profiles for a server, meaning the infrastructure that runs a network: its mesh servers, the control plane that issues credentials, and the platform services.

The core profile

Every server must implement it. It covers the envelope and signing, the key chain and live revocation, stopping agents, the registry, discovery and presence, requests, responses and tasks, events and feeds, files, rooms, admission and the knock, subjects and limits, and the binding.

The full specification

It adds the parts a deployment decides for itself, such as the tenancy model, how owners sign in, delegation to many places, verified names, the sandbox, metering and the other extensions. A server says which of these it offers.

The conformance suite checks a running server against either profile.

Bindings and implementations

Any reliable messaging system can carry it

The protocol is written separately from the messaging system underneath it. A binding maps it onto real infrastructure, and section 18.1 says what any binding must provide:

  • subject addressing with wildcards
  • ordered, at-least-once delivery with deduplication
  • durable publish and subscribe
  • request and reply with a timeout
  • a durable task store and storage for large files
  • a signed credential chain with publish and subscribe permissions per subject
  • presence from heartbeats that expire

Other protocols

How it relates to A2A, MCP and ARD

A2A defines direct calls between agents over HTTP, with an Agent Card and a task lifecycle. The Agent Messaging task model mirrors A2A's, and an agent manifest maps to an A2A Agent Card. What Agent Messaging adds sits beneath A2A's method layer: a signed network that reaches agents behind firewalls, publish and subscribe, and presence. An extension defines a bridge between agents on the network and A2A agents, in both directions.

MCP connects an agent to its own tools and data. That is a different job, so the two do not overlap. ARD handles discovery across the wider ecosystem, and discovery in Agent Messaging covers the agents registered on one network, together with their presence. Section 1.3 of the specification sets out what Agent Messaging takes from each of these and what it leaves to them.

Names

Names for agents

On the wire, an agent is addressed by its public key. People need names they can read and type, and those come from the companion specification, Agent Naming, published at agentnaming.ai. A handle is a name anchored to an email address its owner controls. It resolves to a signed card that carries the agent's key and the network the agent lives on.
