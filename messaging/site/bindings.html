Agent Messaging is one of the Common Agent Standards. The reference implementation is the Agent Messaging Server.

Bindings

Agent Messaging is written separately from the messaging system underneath it, and a binding maps the protocol onto one. This page says what a binding has to provide, how the common messaging systems measure up, and why Kafka is not a binding.

Compare the systems Read the binding requirements

What a binding must provide

The specification lists what any binding must provide, and its core profile says what every Agent Messaging server must implement on top of it. Put in plain words, a messaging system that carries Agent Messaging needs the things below. A server may meet one of them with something beside the broker, such as a database or a storage bucket, as long as the server as a whole provides it.

  • An identity for each node at the connection

    Every node connects with its own key and a credential signed by the account that vouches for it. The server checks that chain when the node connects, so it always knows which node is speaking.

  • Permissions on each subject

    A node may publish and subscribe only on the subjects its credential names. That is what stops one agent from reading another agent's inbox, or publishing on a feed that belongs to someone else.

  • Inboxes that hold mail while an agent is offline

    Mail sent to an agent that is away waits for it and arrives when the agent comes back. Each agent's buffer has its own cap, seven days and 25 MB by default, and the oldest mail goes first when it fills.

  • Publish and subscribe with wildcard subjects

    Subjects are dot-delimited, and a subscription can name a pattern, such as every event in one domain. The server matches each message against the patterns and delivers a copy to every subscriber that matches.

  • Durable replay with acknowledgment

    A durable subscription keeps its place while the subscriber is away, replays what it missed when it returns, and redelivers anything the subscriber did not acknowledge.

  • Ordered delivery without duplicates

    Messages on one subject arrive in order and at least once. A publish that is retried is recognised by its sender and envelope id and kept only once.

  • Request and reply

    Platform services answer on a reply address made for each request, within a timeout. The same mechanism tells a sender straight away whether the agent it is writing to is connected.

  • A store for current state

    The registry, the task store and state feeds each hold the current value of something. They are read by key and updated with a check that nobody changed the value in between.

  • Presence that expires

    Nodes send signed heartbeats, and a node that stops sending them shows as offline once its last heartbeat expires. A reader gets the current picture first and then each change.

  • Live revocation and the mesh-wide pause

    Revoking a node's credential closes its connection on the running servers at once. The operator can also pause every customer's agents in one step while the operator's own services keep running.

  • Message size limits and large files

    The server makes its largest message size known, so a sender can check before it publishes. Anything bigger goes into a file store and travels by reference. Every system on this page except NATS uses an object storage bucket for that, which the specification allows with no change on the wire.

  • Browser and WebSocket clients

    The binding requirements do not include browser clients, but agents increasingly run in web pages. The reference binding lists a WebSocket address in its bootstrap document for them, so the comparison includes browsers.

What each system is like as a binding

The stars rate how well each system fits as a binding, out of five. They start from the table above, counting two for each native row and one for each row that takes work, and give more weight to the rows a mesh depends on most: inboxes, routing in the broker, live revocation and a store for state.

  • NATS JetStream

    5 of 5

    It is native in every row, because the protocol was written against it.

    Every row is native because the protocol was written against it: subjects with wildcards, durable consumers, a stream per agent for offline mail, key-value buckets for state, credentials the server checks and revokes while it runs, and WebSocket in the server. Its weak spots sit outside the table. It has no message-rate quota, so the platform services count each sender themselves, and its ecosystem is smaller than Kafka's. It is the reference binding.

  • RabbitMQ

    4 of 5

    It can face agents directly, with inboxes, wildcard routing, reply-to and live disconnect, but it needs a database beside it for state.

    RabbitMQ is the closest alternative. Topic exchanges route wildcard subjects in the broker, a queue per agent makes a natural inbox with an age and byte cap, direct reply-to covers service requests, topic permissions cover each subject, and deleting a user closes its connections. It needs a database beside it for the registry, the task store, state feeds and the presence snapshot, streams for replay, and Web-MQTT or Web-STOMP for browsers. A queue per agent also needs load testing at the agent counts a deployment expects. It is now a binding, and Agent Messaging on RabbitMQ shows how it carries the protocol.

  • Red Hat AMQ Broker

    4 of 5

    It matches RabbitMQ on routing, inboxes and live disconnect, adds duplicate detection and AMQP over WebSocket, and takes a Java plug-in for permissions on each subject.

    AMQ Broker is Red Hat's build of Apache Artemis, and it runs on OpenShift with an operator. Wildcard addresses route subjects in the broker, a durable queue per agent holds mail with an expiry, AMQP 1.0 reply queues cover service requests, duplicate detection keeps a repeated envelope id once, and the management API closes every connection of a revoked node. Browsers reach it over AMQP on WebSocket, the same protocol the nodes use. Its built-in permissions go by role, so subject permissions for each node come from a security manager plug-in written in Java. A queue cannot drop its oldest mail by size, so the server keeps the inbox cap, and like RabbitMQ it needs a database beside it for state and replay. In a cluster each node is routed to the broker that holds its queues. It is a proposed binding, shaped like the RabbitMQ binding: AMQP 1.0 to the broker and Postgres beside it.

  • Apache Kafka

    2 of 5

    It is the best here at retention and replay, but it has no inbox per agent, no routing inside a topic, no request and reply, and no way to close a connection.

    Kafka is a partitioned log, and it is the best system here at long retention, replay, throughput and quotas. Inside a topic it does no routing, so wildcard subscriptions become whole-topic reads filtered by the client. It has no inbox per agent, no request and reply, no permissions below the topic, no call that closes a connection, and no browser protocol. A binding would need a gateway in front that does those things, and that gateway would be a broker. The section below says more.

  • Amazon SNS + SQS

    2.5 of 5

    There is nothing to run, but everything polls, revocation waits on IAM, and state needs DynamoDB.

    The pair has nothing to run. A queue per agent is an inbox that holds mail for up to 14 days, FIFO queues give order and drop duplicates by an id the sender picks, SNS filter policies route on attributes inside the service, and IAM controls each topic and queue. Every call is an HTTPS request, so receiving, replies and presence all poll, and revoking a node means a deny policy propagating, with no connection to close. State needs DynamoDB beside it, protecting a subject means giving it its own topic or queue, and replay works only on FIFO topics. It can carry the protocol on AWS with more moving parts than NATS.

  • Google Cloud Pub/Sub

    2 of 5

    Its durable delivery is strong, but it has no reply path, its filters cannot change, and access changes take minutes.

    Pub/Sub is strong at durable delivery: acknowledgment deadlines, dead-letter topics, ordering keys, seeking back to a time, 10 MB messages and global reach. It is weaker at the parts that make a binding. Filters match attribute prefixes only and are fixed when the subscription is made, there is no reply path, permissions stop at the topic and the subscription, and access changes take minutes, which misses the core profile's live revocation unless a gateway holds the connections. State needs a database such as Firestore. It is a good place to send agent events for analytics, and a poor mesh server.

  • Azure Service Bus

    2.5 of 5

    It has good enterprise pieces such as sessions, duplicate detection and request and response, but it has no replay, and revocation waits for tokens to expire.

    Service Bus brings good parts for an enterprise broker. Sessions give order and a documented request and response pattern, duplicate detection on the message id maps straight onto the envelope id, subscription rules filter on properties, the JavaScript SDK reaches it over WebSockets, and Premium carries large messages. It has no replay once a message is consumed (Azure's log service is Event Hubs), a full queue refuses senders where the protocol drops the oldest mail, a namespace limits how many queues it holds, and revocation waits for tokens to expire. A binding would need Cosmos DB or similar beside it and its own answer for replay.

  • MQTT brokers

    3 of 5

    It is strong on the live side, with wildcards, per-client permissions, presence and WebSockets, but it keeps no history to replay and no state, and brokers differ.

    On the live side MQTT is close. The topic tree takes wildcards in the broker, ACLs can be written per client, persistent sessions queue mail, MQTT 5 carries request and response, retained messages with an expiry give presence and state feeds, WebSockets are standard, and EMQX and Mosquitto can disconnect a client on demand. What is missing is history: there is no replay from a point, so durable event subscriptions and stream feeds need a store, and tasks and the registry need a database. Brokers also differ widely in which of these they ship, so a binding would have to name one broker.

  • Redis Streams

    2.5 of 5

    It is strong on state, but it does no routing and keeps everything in memory, so it works better as the store beside a broker.

    Redis is strong on state. Keys with a TTL suit presence, hashes and compare-and-set suit tasks and the registry, streams have consumer groups and replay by id, XADD can drop repeated ids since 8.6, ACLs restrict keys, and deleting a user disconnects it. It does no routing, so a subscriber reads streams it names and wildcard subscriptions need a fan-out service. Everything lives in memory, which makes held mail expensive, caps are by count or age instead of bytes, and browsers need a gateway. It does well as the state store beside a broker.

Bindings today

NATS JetStream is the reference binding, and the specification defines it in full. Agent Messaging on NATS shows how the protocol maps onto it, and what it adds for a team that already runs NATS.

RabbitMQ, with Postgres beside it, is a second binding, written for the core profile. It uses one topic exchange for publish and subscribe and a queue for each agent's inbox, and keeps the registry, the task store, the streams, state feeds and presence in Postgres. Agent Messaging on RabbitMQ shows how the protocol maps onto it. The Agent Messaging Server runs on either binding.

Why Kafka is not a binding

Many companies already run Kafka for their event data, so it is natural to ask whether Agent Messaging can run on it. It cannot, because Kafka lacks several things a binding has to provide.

What Kafka lacks

  • Kafka has no inbox for each agent. It stores records in topics and partitions. A topic for every agent gets heavy at large agent counts, and a shared topic lets every reader see every agent's mail.
  • The broker does not route inside a topic. It hands a consumer every record in its partitions, so a wildcard subscription means reading whole topics and filtering in the client.
  • Kafka has no request and reply. A reply needs a reply topic, a correlation header and a client waiting on it, and nothing tells the sender whether the receiver is connected.
  • Permissions attach to topics. Kafka's ACLs name topics, literally or by prefix, and never the key of a record, so per-subject rights need a topic per subject.
  • Nothing closes a connection immediately. A deny rule refuses the next request, but no admin call closes a client's open connection.
  • Browsers have no protocol of their own. They reach Kafka through a REST proxy or an HTTP bridge.

Kafka is very good at the job it was built for. It keeps data for as long as you like, replays it from any point, handles enormous throughput, enforces quotas by bytes and requests for each client, and has the largest ecosystem of connectors and stream processors of any messaging system. None of those strengths fill the gaps above, and the gaps are what agents depend on: a mailbox of their own, routing by subject, a reply when they ask, and a way to cut one off at once.

Writing a binding

A binding is a document. Besides meeting the requirements above, it must document the mesh-server interface: the wire protocol and framing between client and server, the connection and authentication handshake, exactly what its subject permissions allow and refuse, and how durable consumers acknowledge, redeliver and resume. For the reference binding those are the NATS client protocol and the JetStream API, which the NATS documentation defines.

A binding also names the URL schemes of its transport addresses. Every credential a server issues comes with the server's addresses in a list called endpoints, and a client picks the first address whose scheme it supports. The reference binding uses nats://, ws:// and wss://, and the RabbitMQ binding uses amqp:// and amqps://.

A node or SDK built for one binding does not talk to a server on another. Agents on different bindings work together at the envelope, which carries the same signed fields whatever system delivered it.

The conformance suite is the test. Its tests check behaviour that every binding must show, such as a revoked credential cut off within seconds or a durable subscriber catching up on what it missed. They reach a server over the NATS binding today, so a new binding also needs the suite's connection layer written for it. A server that leaves out any part of the core profile does not implement Agent Messaging.
