Agent Messaging is one of the Common Agent Standards. The reference implementation is the Agent Messaging Server.

MCP Events and Agent Messaging

MCP Events is an extension to the Model Context Protocol that lets an MCP client subscribe to events in an upstream system, such as a new email or a production incident, so that an agent can react when nobody is asking. Agent Messaging is a protocol for agents that talk to each other over messaging systems, and its publish and subscribe primitives carry an event from one agent to every agent subscribed to its subject. The table sets out what each specification defines for events, with the section of each that says so.

How the two specifications handle events

MCP Events (beta)Agent Messaging
What it is for Events lets an MCP client subscribe to things that happen in an upstream system, such as a Slack message, a GitHub push or a PagerDuty incident, so that an agent can react when no user is present (MCP Events, Introduction). Publish and subscribe is one of the protocol's three ways for agents to talk, beside inbox messaging and the registry. An agent publishes an event on a subject, and every agent whose subscription matches receives it (Agent Messaging §1, §3.2).
Who sends and who receives An MCP server produces the events and an MCP client receives them. Every events/* request comes from the client (MCP Events, Capability Negotiation). Any agent may publish on the subjects its node is permitted to publish on, and any number of agents may subscribe. The publisher expects no reply (Agent Messaging §3.2, §6.6).
Finding out which events exist The client calls events/list. Each event type has a name, a description, the delivery modes it supports, an inputSchema for subscription arguments and a payloadSchema for its data (MCP Events, Listing Available Events). An agent may list the event subjects it publishes and subscribes to in the emits and accepts fields of its manifest, which makes them discoverable through the registry (Agent Messaging §8.2, §6.6a).
Making and ending a subscription Poll needs no subscribe step and ends when the client stops polling. Push holds one events/stream request open per subscription until it is closed or cancelled, and webhook registers a callback URL with events/subscribe for a lifetime the server grants, ended by events/unsubscribe or by expiry (MCP Events, Delivery Modes, Unsubscribing). An agent subscribes with a subject pattern, and the subscription is an operation on the transport that may be durable or ephemeral. The specification has no message for ending a subscription, so that is done through the transport as its binding documents it (Agent Messaging §6.7, §18.1).
How events reach the receiver Each event type offers one or more of three modes, and none is mandatory: poll with events/poll, push on a long-lived events/stream request, and webhook, where the server POSTs each event to a callback URL (MCP Events, Delivery Modes). The transport pushes each event to every subscriber whose pattern matches, and the agent's onEvent handler runs for each one (Agent Messaging §3.3, §6.7).
Guarantees and ordering Delivery is at least once when the event type has a durable upstream and the client resumes from its last cursor, and emit-only event types are at most once across server restarts. Poll and push keep order within a subscription, webhook order is best effort, and nothing orders events across subscriptions (MCP Events, Ordering and Delivery Guarantees). Every binding must deliver in order within a subject and at least once, with deduplication on the sender and the message id. Durable subscriptions acknowledge each event explicitly, and order across subjects is not guaranteed (Agent Messaging §5.4, §6.7, §18.1).
Retries and duplicates A webhook server retries each event on its own with exponential backoff for a bounded number of attempts, and the receiver drops repeated deliveries by webhook-id. Within a subscription, eventId identifies the upstream event so the client can discard duplicates (MCP Events, Webhook event delivery, Event Occurrences). In the reference binding an event that is not acknowledged within 30 seconds is delivered again, up to five times in all. Receivers must keep a bounded memory of the sender and message id pairs they have handled and drop repeats, on event subscriptions as on the inbox (Agent Messaging §18.6, §22.1, §22.2).
When the receiver is away The client resumes from its stored cursor, and the server replays from that position when the upstream keeps history, or answers truncated: true when it cannot. A webhook callback can be a forwarding proxy that receives events and serves them to the client by poll or push (MCP Events, Cursor Lifecycle, Webhook-Based Delivery). A durable subscription replays what was published while the agent was away. The reference binding keeps a domain event for at most 24 hours, and keeps it at all only if a durable consumer or source already has interest in its subject (Agent Messaging §3.2, §6.7, §18.3).
Durability and replay Replay is optional for each event type, and a type with no addressable history returns cursor: null and always starts from now. A client can pass maxAgeMs to cap how far back a replay reaches (MCP Events, Cursor Lifecycle). Events must be stored durably for replay. A feed is either a stream, an ordered history that subscribers replay, or a state, whose latest value a late subscriber can read without the history (Agent Messaging §6.6, §6.6a).
Identity and signing Webhook deliveries carry a Standard Webhooks HMAC signature made with a secret the client supplies for each subscription, and a server may add an Ed25519 signature whose key it publishes on its Server Card. The extension defines no signature for poll or push results (MCP Events, Webhook security). Every event is an envelope signed with the publishing agent's Ed25519 key, and the receiver must verify it against the key in from. Underneath, the transport authenticates the node's connection with a credential that chains to the operator (Agent Messaging §4.5, §4.6, §5.3).
Authorization and who may subscribe When the caller is authenticated, the server must check that it may subscribe to the event type with those arguments, should check again during delivery, and ends the subscription if access is revoked. Webhook requires an authenticated principal, and receiving an event never authorizes the agent to act (MCP Events, Authorization, Subscription identity). The transport enforces the subjects each node may publish and subscribe on, as its credential lists them, and only the node that vouches for a feed's owner may publish to that feed. Receivers base their own decisions on the verified sender (Agent Messaging §4.6, §6.6a, §14.3).
Event shape and typing An occurrence is {eventId, name, timestamp, data, cursor}, and data follows the event type's payloadSchema, a JSON Schema. Schemas should change only by addition, and a breaking change uses a new event name (MCP Events, Event Occurrences, Listing Available Events). An event is an emit envelope whose payload holds domain, event_type, an optional A2A Task id and data, published on mesh.event.{domain}.{event_type}. The specification does not define a schema for data (Agent Messaging §5.1, §6.6).
Filtering Subscription arguments, checked against the event type's inputSchema, can filter or transform the events, for example by sender or by severity (MCP Events, Listing Available Events). Subscribers filter by subject pattern, where * matches one token and > matches one or more, as in mesh.event.scraping.*. The specification defines no filtering on an event's content (Agent Messaging §6.7, §14.2).
Transport Poll and push run over MCP's Streamable HTTP and stdio transports, with push as a server-sent event stream or as notifications on stdout. Webhook deliveries are HTTPS POSTs, and callback URLs must use https (MCP Events, Push-Based Delivery, Webhook security). Events travel on a messaging system through a binding, which must provide subject addressing, ordered at-least-once delivery and durable subscriptions. NATS JetStream is the reference binding, and a RabbitMQ binding also exists (Agent Messaging §18, §18.1).
Confidentiality and untrusted content Payloads are untrusted data that can carry prompt injection, so clients should sanitize or sandbox them before a model reads them, and servers should send only enough to identify and triage an event (MCP Events, Security Considerations). Events are open broadcast that every permitted subscriber and the transport can read, so content that needs sealing must travel in a request. Receivers apply their inbound protections to events too, including a size cap and fencing that marks which text a sender wrote (Agent Messaging §6.6, §22.1, §22.6).
Version and status Stage "Beta", extension identifier io.modelcontextprotocol/events, defined by SEP-3415, for MCP protocol revision 2026-07-28 and later. A server advertises it in its server/discover capabilities (MCP Events, Introduction, Capability Negotiation). Version 0.12.0-draft, whose status the document gives as "Working Draft". Every envelope carries the wire version in v, currently 0.4.0, and a receiver refuses an unsupported major version (Agent Messaging title block, §20.1, §20.2).
