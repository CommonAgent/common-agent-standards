## 0.9.7-draft (2026-10-20)

Section 10.8's `canceled_by` is now either verified or unverified, and the server never confirms that the original requester did not ask for a cancel until it can know. A verified attribution is `party`, `requester_request` and `at`, with an optional `resolved_at`. An unverified one is `party`, `at`, `unverified: true` and `unverified_reason`, with no `requester_request`, and a reader tests `unverified` first. A missing `requester_request` means unknown, and only an explicit null says that the requester did not ask. A server never writes null at the transition: a settle writes it only when it runs at least the grace period G after `at` and before `at` plus 24 hours, the reads worked, and no cancel request for the Task is marked received and unwritten, so a null always carries `resolved_at`. The reasons are `settling`, `read_failed`, `read_timed_out`, `ledger_unavailable`, `window_incomplete`, `expired` and `no_origin`. A canceled update the requester signed is the requester asking, with `via` set to `update`. The server keeps up to 8 cancel requests per Task, sender and addressee, uses the earliest received one that counts, and reads more than 8 as `window_incomplete`. A settle is announced on `mesh.event.task.canceled_by_settled` at least once, and a consumer dedupes it on `task_id` plus `canceled_by.resolved_at`. Every task-manager instance must use the same G. Section 7.1 describes the two shapes, and Section 18.4's `mesh_task_origins` row gains the keys the settle uses. `conformance/task-origin.json` is the released Agent Messaging Server 0.4.3's file. The minimal contracting profile moves to 0.5.3-draft and applies to this version, and the Common Agent Specification 0.28.11-draft publishes it on commonagent.net. The Change History entry of 2026-10-20 in [SPEC.md](SPEC.md) has the details. The wire version stays 0.3.0.

## 0.9.6-draft (2026-10-20)

Section 7.1's Task object gains two optional members that the platform writes and a party never does. `origin` is the request that created the Task, as the server observed it routing that request: `request_id`, `requester`, `responder`, `offering`, `observed_at` and `bound_by` (`request` or `answer`). A party's update cannot set, change or remove it, it is not part of `history` and is not trimmed with it, and when it is absent the request is unknown. It attaches only when its parties are the Task's parties, a Task id binds to one request and a request to one Task id, and the first observation wins. Only a request's first answer that is not an accept or a delivery signal may bind it, the first binding of a Task id stands a request is tied to a Task only when the responder's answer carried that Task id, a request that named the Task id itself is the requester's choice and never evidence, every other request of the Task's requester answered with it binds nothing and is listed in the optional `contested_by` (at most 256 ids, with `contested_overflow` and `contested_overflow_since` past that, and on the Task itself when it has no origin), other askers' requests answered under the Task go in the optional `contested_by_asker` (at most 64 askers, with `askers_overflow` and `askers_overflow_since`), a requester's read shows only its own origin, contests and cancel attribution, one Task id runs one piece of work, so a responder resolves the requests naming one Task id one at a time in arrival order and must refuse the same requester's second request naming it while its stream still runs, the optional `origin.multiple_requests` lists the same requester's requests that named a stream-created Task's id and were answered under it, lifecycle events carry `origin` without the contest fields or `multiple_requests`, `origin_mismatch` marks a Task whose recorded requester differs from the observed one, and the server observes only what reaches the addressee's inbox. Section 10.8 gives a canceled Task `canceled_by`: `party`, the side that signed the canceled update; `requester_request`, the original requester's own canceled update or the first `task.cancel` request the server observed from it, or null; and `at`. The signed `reason` remains the signer's own claim. Section 18.4's bucket table gains `mesh_task_origins`, which holds no content and expires after seven days with the Task records. `conformance/task-origin.json` pins the names, shapes, closed values and cases. The minimal contracting profile moves to 0.5.2-draft and applies to this version, and the Common Agent Specification 0.28.10-draft publishes it on commonagent.net. The Change History entry of 2026-10-20 in [SPEC.md](SPEC.md) has the details. The wire version stays 0.3.0.

## 0.9.5-draft (2026-10-20)

Section 13.5, metering, gives the meter event an optional `request_id` member: the id of the request envelope that the event's deriving envelope answers. A metering deployment SHOULD set it on every event it derives from an answer, which is the `responses` and `bytes_out` events of a `respond`, the declared events lifted from a usage receipt (on a `respond`, or on a request carrying `in_reply_to`) and the refusal event. With it, a reader folding the stream joins a request's events to its answer's, such as a request's fee to its answer's outcome, without correlation state of its own. The events of a delivered request need no such member, because their `envelope_id` is the request's id. The idempotency key stays (`meter`, `envelope_id`), and a reader that does not know the member ignores it. `conformance/metering.json` gains a `request_id` group with valid events and the join of one exchange. The minimal contracting profile moves to 0.4.1-draft and applies to this version, and the Common Agent Specification 0.28.6-draft publishes it on commonagent.net. The Change History entry of 2026-10-20 in [SPEC.md](SPEC.md) has the details. The wire version stays 0.3.0.

## 0.9.4-draft (2026-10-19)

Section 19.2, the task receipt, gains an optional `buyer_reference` member. When a task was admitted under an agreement that carries the client's own reference for its accounts, such as an Agent SoW engagement's `buyer_reference` (Agent SoW 0.25.0-draft, Section 5.17), the receipt carries that reference byte for byte from the version of the agreement the task was admitted under, so a client's accounting system can match each task to its purchase order. A canceled task's receipt carries it the same way. The platform does not interpret it. No other requirement, field, wire identifier or section number changes. The Change History entry of 2026-10-19 in [SPEC.md](SPEC.md) has the details. The wire version stays 0.3.0.

## 0.9.1-draft (2026-10-17)

Section 5.7, messages for the person behind an agent, now reads whom an agent acts for from the Common Agent Specification's `acts_for` (its Sections 6.2 and 6.9). Only an agent whose `acts_for` is `person` declares the extension `mesh://extensions/audience/v1`. Every other receiver written to this version refuses a message marked for a person at its door with `AUDIENCE_NOT_SUPPORTED`, carrying `details.reason` and `details.acts_for`, so the sender never waits for a person who is not there. A sending SDK that finds an `acts_for` other than `person` in a receiver's Descriptor treats the receiver as not declaring the extension. Appendix D, Section 12.2 and the extension registry say the same, and `conformance/audience.json` and its checker gain the door's cases. The Change History entry of 2026-10-17 in [SPEC.md](SPEC.md) has the details. The wire version stays 0.3.0.
