# Changelog

Every version of the Common Agent Specification and what it changed, newest first. Each entry was written into the specification when its version was drafted, and is reproduced here word for word. A version is tagged in the Common Agent Standards repository as `common-agent-v` followed by the version, such as `common-agent-v0.26.0-draft`, and the text of [SPEC.md](SPEC.md) at that tag is the text of that version. Versions before 0.26.0-draft were drafted before the specification moved to this repository and have no tags here.

## 0.35.0-draft (2026-10-24)

Section 8.8, security events (8.8.1) and quarantine (8.8.2), is adopted as proposed in 0.34.0-draft and is now part of the specification, so its MUST and SHOULD bind. The paragraph that marked it proposed and outside conformance is removed, and its heading no longer says proposed. The text is otherwise unchanged: the closed list keeps its fifteen acts, with the three approval events `approval_asked`, `approval_given` and `approval_refused` kept separate, and a node that can neither reach its event sink nor keep events locally still refuses new jobs with `events_unrecorded` and holds its running jobs. Agent Messaging 0.9.16-draft adopts its §13.6, which carries the quarantine act. On commonagent.net, the old anchor of the section's heading still lands on it, and code in a table cell, such as an event name, no longer breaks in the middle of a word. The minor version moves because conformance now requires what Section 8.8 says. No member, attribute or section number changes.

## 0.34.0-draft (2026-10-24)

A proposal for review, with no change to what conformance requires. A new Section 8.8, marked proposed and outside conformance until a later version adopts it, drafts two records. A security event (8.8.1, tag `agent-security-event-v1`) is a small signed record of one moment a boundary refused, held or let something through, from a closed list of fifteen acts: `admission_refused`, `screening_flagged`, `scope_refused`, `signature_failed`, `package_refused`, `credential_used`, `ceiling_hit`, `egress_denied`, `approval_asked`, `approval_given`, `approval_refused`, `stop_pressed`, `stop_lifted`, `outputs_quarantined` and `quarantine_ended`. Each carries the subject, the emitter, the job's trace id or task id, the policy version where one decided, and a reason code drawn from the refusals and records the specification already defines, and carries shapes only. Whoever applies a check emits its event, never the subject; events are private to the owner; and a node that can neither reach its sink nor keep events locally starts no job. A quarantine (8.8.2, tag `agent-quarantine-v1`) is a signed act by the subject's owner or its platform that marks delivered outputs as suspect, by job manifest, by time window, or since an `agent_version` or package digest, with `release` and `confirm` acts; recipients' nodes hold or flag the covered pieces and never delete them. Agent Messaging 0.9.15-draft proposes how the act travels on its advisory channel.

## 0.33.0-draft (2026-10-24)

The deployment record (Section 8.3) names the Descriptor bound before and after every act that changes a running agent, as it already did for an update. On a rollback, `rolled_back_from` gains `descriptor_digest`, the digest of the Descriptor bound before the rollback, as `updated_from` carries it on an update. On a reconfigure, a new member, `reconfigured_from`, carries `descriptor_digest`, the digest of the Descriptor bound before the change, and no package members, because a reconfigure leaves `package` unchanged; where the change bound no new Descriptor, the two digests are equal. `descriptor_digest` still names the Descriptor bound after the act. The Roll back and Reconfigure paragraphs of Section 12.7 say so. This adds a member and a member's member, so a record that was valid under 0.32.0-draft is valid under this version. No attribute or section number changes.

## 0.32.0-draft (2026-10-24)

The deployment record (Section 8.3) gains the act `update`, a newer version installed in place of the current one under the same subject, which Section 12.7 already described and the deployment manager of Agent Roles already recorded. On an update, `package` names the new version and a new member, `updated_from`, names the version the agent left, with the same members as `package` and the `descriptor_digest` of the Descriptor bound before the update, so the record names both package digests and both Descriptor digests, as 12.7 requires. `descriptor_digest` names the Descriptor bound after an update, a rollback or a reconfigure. The act list of 8.3 now says in a few words what `deploy` and `remove` record, and the Install, Update and Remove paragraphs of 12.7 name the act each one records, so every act 12.7 describes has its value in 8.3, and 12.7 names the act of every value. This adds an allowed value and a member, so a record that was valid under 0.31.0-draft is valid under this version. No attribute or section number changes.

## 0.31.0-draft (2026-10-24)

The deployment record (Section 8.3) follows Agent Roles v1.3. Its `act` gains `rollback`, the agent returned to the version it ran before the current one, and `reconfigure`, the settings, credentials or ceilings of a running agent changed with no new version. Two members are added with the meaning the deployment manager of Agent Roles gives them: `rolled_back_from`, which on a rollback names the version the agent left, while `package` names the version it returned to; and `changed`, which on a reconfigure lists each change with `what`, `before` and `after`, credentials by name only. `ceilings` now covers the ceilings a reconfigure set as well as those a deploy set. `environment` allows `dev` beside `test`, `staging` and `production`. Section 12.7 no longer calls a rollback an update. Roll back is its own recorded act: it goes through an update's steps and check under the same subject, and it is the one act in which `agent_version` decreases. A new Reconfigure paragraph says what a reconfigure may change: the version and the subject MUST NOT change, an offering's ceilings MAY be lowered and MUST NOT be raised, and a change to a member of the bound Descriptor that the install decides binds a new Descriptor. Section 6.5 says such a Descriptor keeps its `agent_version`, because the package has not changed. A rollback to a version installed alongside makes that version the current one. These add allowed values, members and acts, so a record that was valid under 0.30.2-draft is valid under this version. No attribute or section number changes.

## 0.30.0-draft (2026-10-24)

## 0.29.0-draft (2026-10-22)

External inputs say what the caller grants. Section 6.2 gains three optional members on an input marked `external: true`, the caller's own resource that the caller names in a request: `access`, in the vocabulary of `systems[].access` (`read`, `write`, `trigger`); `grant`, how the caller gives the access, `identity` (the caller adds an identity the platform shows them, and no key is shared) or `key` (the caller supplies a secret the platform keeps in the caller's key store or its own), with `oauth` reserved and not defined; and `provider`, the product the resource lives in, such as `google-analytics`, a name and never an address or an account identifier. An unlisted value of `access` or `grant`, `oauth` included, is read as not stated, and where an input carries both `grant` and `via`, `via` SHOULD include the matching mechanism (`seat` for `identity`, `api_token` for `key`), or `grant` is read as not stated. A caller's grant is not an install setting: the platform hands it to that caller's runs only. A platform MUST give each caller's grant its own identity or its own secret, and an agent working for one caller MUST reach that caller's resource through that caller's grant only, so one caller can never reach another caller's resource through a shared agent. Rule 3 of Section 6.4 names product names among the shapes a Descriptor carries, Section 9 renders an external input that carries `grant` as a grant, and rules 2 and 7 of Section 12.6 allow a script to reach an external input's resource through the caller's grant. The section gains an example, a web analytics agent. No other requirement, member, attribute or section number changes.

## 0.28.0-draft (2026-10-17)

the Agent Descriptor on the floor. Every agent serves a bound, signed Agent Descriptor, and a new Section 4.9 says so: the Descriptor is bound with its `subject` filled, carries the subject's `descriptor-statement-v1` signature, and holds at least the minimal Descriptor. Section 6.2 defines the minimal Descriptor as the members the floor reads: `format`, `agent_version`, `subject` (with `id`, and `handle` where one is held), `does`, `acts_for`, `offerings[]` and `signatures`. An empty `offerings[]` is a statement that the agent takes no work, so a bare agent or a guest serves a minimal Descriptor too. Each offering carries `id`, `name`, `inputs[]` and `outputs[]`, and SHOULD carry `does`, its one sentence, which is the member's name from this version on. The description of Section 4.2 and the five questions of Section 4.3 are answered from that Descriptor and the signed documents it points to, and the table of Section 4.3 names the member each answer comes from. Entryway exchange 2 (Section 4.4) always answers with the document, and the answer "the operator has published none" does not conform. Section 6.6 makes the signature a MUST, Section 6.7 makes answering a request for the Descriptor a MUST, Section 6.8's check covers the minimal members, Section 8.3's `descriptor_digest` is expected on every deploy that starts an agent, and Section 12.7's install adds `acts_for` when it binds the draft.

Section 10: Described, the attribute for serving a bound, signed Descriptor, is part of the floor, so no agent earns it, and the attributes number twenty. The heading is "The twenty attributes", and the profile "hireable by a stranger" does not list it.

Section 6.12 removes `shape`, as 0.27.0-draft said it would. A writer does not emit it, a reader ignores it as an unknown member, a checker reports it, and the section keeps a table of where each former member went. The Descriptor's own mapping of `shape` into the AgentDoc goes from Section 9.4.

Section 6.9 follows Agent Messaging 0.9.1-draft on messages for a person: only an agent that acts for a person has a person behind it, and that person is its owner. An organization's agent, a public service, and an agent whose `acts_for` is not stated have no person behind them, do not say that they keep those rules, and refuse a message marked for a person at the door. An organization does not name a reader for such messages.

Conformance: a new fixture, conformance/descriptor-floor.json, holds Descriptors that meet the floor and Descriptors that do not, with signatures that really verify, and the answers to exchange 2, with conformance/lib/check-descriptor-floor.mjs to check it. conformance/offering-scope.json moves to version 2: offerings carry `does`, and `shape` is ignored and reported.

## 0.27.0-draft (2026-10-17)

whom an agent acts for, what an offering may be asked, and what it can touch. Section 6.2 gains `acts_for`, REQUIRED in a bound Descriptor: `person`, a personal agent, the same thing Section 7.8 and PACT call one; `organization`, a business or team agent, which MAY name the organization in `organization_name`; and `anyone`, a public service with no principal. It is decided at install, so a draft carries none, and a Descriptor without it, including every one written before this version, is read as not stated and never guessed. Section 6.9 ties it to the consent rules: a connection of the door (Section 7.1) is offered only between agents that act for a person, and where the other side's `acts_for` is not stated the person deciding is shown so; only an agent that acts for a person acts on a person's grants, and a business's agent behind a PACT Provider declares `organization`; and the person behind an agent who reads messages marked for a person (Agent Messaging, Section 5.7) is its owner, whoever the organization names, or nobody for an agent that acts for anyone. Sections 7.1 and 7.8 cite it. `interaction` is narrowed to one question, whether a person is attending the agent right now, and Section 9.5 no longer calls it the service-or-personal axis; its caller-side semantics are cited to Section 6.9, where they are.

Section 6.11 gives each offering a `scope`. `task-specific` is named work with typed inputs and outputs, and it is what an offering without `scope` means, so every existing Descriptor stays valid. `open-with-focus` takes any instruction within a stated focus and declares its `focus`, one of `software`, `documents`, `data`, `research` and `operations`, with a `role` from the Agent Roles registry recommended; its `workspace[]`, the shared resources of Section 5.3 it works in, as shapes; its `authority`; its deliverables in `outputs[]`; and its `ceilings`. `open-ended` takes any instruction, declares its authority and ceilings, has its agent declare data use, and makes no claim about what it can do. An unrecognised scope reads as `open-ended`. One agent may mix scopes, and any agent-level summary is derived from its offerings. `authority` is a closed list of what an offering can touch: `reads-files`, `writes-files`, `reads-systems`, `updates-systems`, `triggers-systems`, `runs-commands`, `reaches-network`, `sends-messages` and `spends-money`, built on resource access, `systems[]` access levels and the connection grants, with `authority_decided_by` saying what keeps a running job inside it. `ceilings` bound one job (`job_seconds`, `cost_per_job`, `spend_per_job`, `messages_per_job`), each as `{ most, decided_by }`, and an install may lower them and never raise them; the Descriptor's `limits` may take the same form.

Section 4.6 keeps the rule that there is no default route: an open offering is still a named offering that a request names, and the boundary checks, by rule and in order, the offering, the workspace, the authority the request allows (a request may narrow it with `authority`, and one that allows `spends-money` carries `spend_limit`), and the budget. The refusal is `SCOPE_REFUSED`, with `reason` `workspace`, `authority`, `spend_limit` or `focus`. Section 4.7 has every refusal carry `decided_by`, `rule`, `model` or `person`, so a reader knows whether code enforced it or a model judged it; "that is outside my focus" is decided by the model, and a refusal without the member is read as not stated.

Testing follows scope. A task-specific offering is tested case by case as before; an open-with-focus offering against an evaluation set for its focus, which Section 8.4's evaluation record now names in `evaluation_set` with its `result`; and an open-ended offering only on its limits, with no capability case allowed. The record gains `offering` and `scope`, and its refusal cases record `decided_by`. Directories do not match open-ended offerings by a search for the work wanted. The AgentDoc's `sells` carries every offering's `scope`, derives `sells.scopes`, labels open offerings in words, does not present what an offering will try as what it can do, and shows a ceiling as enforced only when a rule decides it and `visibility` allows. Sections 9.8 and 9.10 gain the matching rendering rule and checks. A new fixture, conformance/offering-scope.json, pins the declaration checks, the boundary cases, the `decided_by` of each refusal, the mapping below, and the directory rule.

Section 6.12 takes the Descriptor's `shape` apart, because it described the agent's inside and this specification describes the outside. `kind` is removed, and `decided_by` answers its real question; a deployment record may still say what was installed, as background, in the new optional `installed` (Section 8.3), and Section 9.5.1 loses the `kind` table and keeps `visibility`. `memory` moves into data use beside retention (Section 6.9) as `remembers-across-jobs` or `starts-clean-each-job`. `model` maps to data use `processors`. `steps` is replaced by `scope` and `tools_runtime` by `authority`, and neither maps to a value, since each was a fact about the inside. `fleet` becomes a member at the level of the agent's identity, and the AgentDoc carries it and `acts_for` in `identity`. `harness` stays in deployment records only, in `target`. For this revision readers accept the old members and map them as Section 6.12's table says, and writers emit the new ones; the old members are removed in 0.28.0-draft. The AgentDoc's `shape` section keeps its name and now carries `interaction` and `visibility`. In the package chapter, a draft carries each offering's scope, authority and ceilings and no `acts_for` (Sections 12.3 and 12.6, rule 4), the install decides `acts_for`, `interaction` and `fleet` and may lower ceilings (rule 6), and Section 12.10 checks the new members.

The floor. Section 4's opening now says that every requirement in it applies to every agent, and that an optional capability, with the rules that come with choosing it, lives in Section 7. The encryption key, which sat in Section 4.1 as an optional capability inside the floor, moves to Section 7.2 with sealing: the X25519 key distinct from the signing key, the signed key claim required wherever one is declared, cleartext only where none is, and where sealing ends. Section 4.1 keeps one sentence that points there, and Sections 6.9 and 10 and Appendix A follow.

## 0.23.0-draft (2026-10-07)
